## Why pull-based

{/*
  Slide 2, your framing:
  - Dask scheduler is push-based and Python-bound. Single Python process, so
    task assignment / dependency tracking / worker state / result routing all
    serialize on one thread.
  - At AGC / 200 Gbps scale, that control plane is where pressure shows up.
  - Dask scheduler state is in memory. Stop it, it's gone.
  - hq: pull-based, workers fetch, server pushes nothing. Opaque cloudpickle
    tasks over HTTP(S). Redis snapshots queue + task state to disk. hq-server
    holds no authoritative state.
  - Your line, worth keeping: existing HEP tools typically do NOT support
    stop-and-resume. Ctrl+C for the day, come back, continue.
  - Load balancing falls out for free: more workers, they fight to empty the
    queue.
*/}

## What it did not survive

{/*
  Slide 5 — the honest slide, and the reason this talk is worth an entry.
  - queued task, worker dies → any live worker picks it up. Fine.
  - CLAIMED task, worker dies → ~30s heartbeat timeout marks it lost. NOT
    requeued.
  - ownership already tracked in workers:running:{workerId}. Redis knows who
    held what. Nothing acts on it.
  - your proposed fix: on timeout, reset each task that worker owned to queued
    + LPUSH
  - caveats you listed yourself (at-least-once):
      · slow worker may finish after requeue → duplicates → side effects must
        be idempotent
      · HQ_WORKER_TIMEOUT too aggressive → false timeouts
      · poison tasks need max-attempts / dead-letter

  Connect forward if you want: in August you wrote histserv with an idempotent
  per-chunk_id flush — i.e. you later built for exactly this. See /papers/hq.
