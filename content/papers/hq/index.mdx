## Overview

`hq` is a pull-based task queue for high-energy-physics analysis, prototyped by
Peter Fackeldey as an alternative to `dask-distributed` for large task graphs.
Workers fetch work over HTTP; the server tracks no worker pool and pushes
nothing. Redis holds the queue and the task state, and snapshots both to disk.

I spent the summer of 2026 on it as an IRIS-HEP fellow, mentored by Peter
Fackeldey (Princeton) and Oksana Shadura (UNL), with the target being
deployment at analysis facilities — coffea-casa specifically, ahead of the
HL-LHC.

The architecture was not mine and the idea was not mine. The distance between
"a prototype that works on its author's machine" and "a thing another person
can deploy and trust" was the work.

## What I contributed

Roughly in order, because the order is the argument:

**Making it deployable.** TLS on the HTTP boundary and an HTTPS option for the
server, with certificates discovered through environment variables rather than
hardcoded paths, and `verify=` wired through both the client and the worker. I
also split `client/` and `worker/` into separate directories, which sounds like
tidying and is not: they are separately installable things with different
dependencies, and a facility deploys them to different machines.

**Giving it an executor.** `HQExecutor` is a single context manager — it takes
a queue of its own, spawns workers, exposes `submit`/`map`, waits until
everything reaches a terminal state, and cleans up. Queue names are UUID7, so
two people (or two runs) sharing one server cannot collide. Before this, using
`hq` meant orchestrating those steps by hand.

**Closing the result path.** Workers write their results as pickles to a shared
filesystem under `HQ_RESULT_DIR/{queue}/{id}.pkl`, and the client gathers the
return values rather than only polling for status. A queue that tells you a task
succeeded but not what it produced is not usable for analysis, and this was the
gap that had to close before anything could merge histograms.

**Proving it on a real workload.** I brought the CMS Open Data ttbar Analysis
Grand Challenge pipeline onto `hq` — Coffea runner and ship smoke tests,
cabinetry configurations, and a benchmark comparing `hq` against Python
futures. The AGC is the field's standard "does this actually work" workload,
and running it is a different claim from running a synthetic `map`. The
pipeline now lives in its own repository, [agc-hq](https://github.com/ijohnkojo/agc-hq).

**Writing it down.** A documented architecture and operations set — deployment,
configuration, the executor, the result path — plus `scripts/testrun.sh`, which
brings up Redis, the server over TLS, workers and a client in one command. The
documentation lives in [hq_docs](https://github.com/ijohnkojo/hq_docs). This is
the part that decides whether anybody else ever runs the thing.

**A histogram service.** `histserv`, a server-side option for histogram
handling, with its own smoke test and documentation.

## What I did not do

Worth stating, because the repository contains it and I did not write it:
per-task subprocess environments, peak-RSS tracking, the Redis Streams work
with its consumer groups and fault recovery, and heartbeat telemetry. Several
of these appear in my own talks as roadmap items rather than results, which is
where they belonged at the time.

## Technical details

The stack is deliberately mixed: a TypeScript server on Bun, a Python client
and worker managed with `uv`, and Redis for the queue and state — with
Dragonfly usable as a drop-in.

The tradeoffs the design accepts are real and are not hidden. Pickup latency is
bounded by the poll interval, roughly a second. There is no locality-aware
scheduling; a worker takes the next task, not the nearest one. And when a worker
dies holding a claimed task, that task is marked lost rather than requeued —
the ownership record exists in Redis, but at the time of writing nothing acts
on it. I proposed requeue-on-timeout as the fix and
[demonstrated the failure live](/presentations/hq-agc-demo-day) rather than
describing it.

What the design buys in exchange is cheap networking, workers that can join and
leave freely — which suits opportunistic HTCondor slots — and durable
stop-and-resume, which most tooling in this space simply does not offer.
